# Gotcha (잡았다 요놈) — examshield

로컬에 있는 시험 문서(PDF, Word, 한글)를 내용은 그대로 둔 채, 텍스트를 복사해 AI에 넣는 것을 막고 유출되면 누구의 복사본인지 추적할 수 있게 재가공하며, 그 효과를 날짜와 모델 버전이 찍힌 수치로 보여주는 오프라인 CLI.

> **상태: 초기 개발 (Phase 7까지 구현. 실제 AI, 실제 인쇄·촬영, 폐쇄망 PC로 확인하는 일이 남음).**
> 복사본을 만드는 `protect`, 내용이 같은지 검사하는 `check`, 효과를 재는 `verify`와 `report`, 유출본의 수험번호를 찾는 `trace`, 프로파일과 검증 상태를 보여주는 `profile`, 인쇄물 사진의 촬영 조건을 재는 `calibrate`, 이 PC에서만 열리는 웹 화면 `ui`가 동작한다. 실제 AI로 잰 것은 Claude(`claude-opus-5-5`) 한 모델, 프로파일 두 개뿐이다(2026-11-21). 결과는 "텍스트를 복사해 붙이는 경로만 막고, 화면 캡처와 파일 올리기는 막지 못한다"였다. OpenAI와 Google 모델로는 호출해 본 적이 없다.
> Phase 1~5와 인쇄 시험용 Phase 6을 만들었다. 잰 두 프로파일 가운데 `a-remap-decoy`는 텍스트 복사 경로만 막았고 `a-decoy`는 아무 경로도 막지 못했다. 나머지는 실제 AI로 잰 적이 없다. 그래서 `protect`는 모든 `a-`, `b-` 프로파일에 경고를 낸다. 인쇄 시험 기능은 시뮬레이션으로만 확인했고 실제로 인쇄해서 찍어 본 적은 없다.

## 개요

스마트안경과 생성형 AI를 쓴 시험 부정행위가 국내에서 잇따라 적발됐다. 지금 시행 중인 대책은 모두 기기 단속이고, 시험지 자체를 다루는 대책은 찾지 못했다. 이 도구는 그 빈자리를 겨냥한다. 배경은 [spec/02-background.md](spec/02-background.md)에 있다.

하는 일은 세 가지다.

1. 시험 문서를 내용이 같은 복사본으로 바꾼다. 텍스트 레이어 교란, 숨은 미끼, 수험번호별 추적 워터마크를 넣는다.
2. 원본과 복사본의 내용이 같은지 기계로 검사한다.
3. 복사본이 AI 판독과 풀이에 얼마나 저항하는지 모델별로 측정해 리포트로 남긴다.

**이 도구는 "AI가 못 읽는다"를 약속하지 않는다. "이 날짜, 이 모델들 기준으로 판독률이 몇 %였다"를 약속한다.** 교란 기법의 효과는 전부 가설이고, 측정해서 살아남은 것만 쓴다.

대상은 온라인 시험이나 과제 파일을 배포하는 교사, 출제자, 평가 기관이다.

### 동작 방식

- **변환은 네트워크 없이**: `protect`와 `check`는 네트워크 호출이 0건이다. 테스트에서 소켓 생성을 막고 통과하는지 본다.
- **원본은 그대로**: 원본은 읽기 전용으로 열고, 결과는 항상 다른 폴더에 쓴다.
- **같은 입력이면 같은 출력**: 입력, 프로파일, 시드가 같으면 복사본이 바이트 단위로 같다.
- **검증 대상은 문서가 아니라 프로파일**: `verify`는 내장된 공개 문항 세트에 프로파일을 적용해 측정한다. 실제 시험지는 클라우드로 보내지 않는다.
- **API 키는 사용자 것**: 클라우드 검증은 선택 사항이다. 키는 환경변수나 OS 키체인에서 읽고, 평문 파일에 쓰지 않는다.
- **효과에는 유효기간이 있다**: 검증 결과는 그날 그 모델을 상대로 잰 값이다. `protect`는 프로파일의 최신 검증 리포트를 찾아, 없거나 30일이 넘었거나 기준에 못 미치면 경고한다. 경고는 복사본을 막지 않는다.

보안 요구사항 전체는 [spec/05-security.md](spec/05-security.md)에 있다.

## 요구 사항

- Python **3.11 이상** (개발은 3.12)
- [uv](https://docs.astral.sh/uv/)
- Git
- 선택: [Tesseract](https://github.com/tesseract-ocr/tesseract)와 `kor`, `eng` 데이터 (OCR 기준선), [Ollama](https://ollama.com)와 비전 모델 (로컬 모델 측정), LibreOffice (Word, 한글 입력)

## 설치

아직 패키지로 배포하지 않았다. 소스에서 설치한다.

```bash
git clone https://github.com/Trapa-Eureka/Gotcha.git
cd Gotcha
uv sync
```

PyPI에는 아직 올리지 않았다. 올리면 다음처럼 설치할 수 있게 할 예정이다.

```bash
uv tool install examshield
```

Python과 uv가 없는 PC에서 쓰려면 실행 파일 하나로 만든다. macOS에서만 된다.

```bash
uv sync
packaging/build-macos.sh    # dist/examshield (약 120MB)
```

만든 파일을 다른 맥으로 옮겨 그대로 실행한다. Tesseract와 LibreOffice는 들어 있지 않다. 그 PC에 따로 설치돼 있으면 찾아 쓰고, 없어도 PDF 처리는 된다.

## 빠른 시작

[설치](#설치)를 마친 뒤, 저장소 폴더에서 실행한다.

```bash
uv run examshield protect 시험지.pdf --out out/copies --profile a-remap-decoy  # 복사본을 만들고 바로 검사
uv run examshield check 시험지.pdf out/copies/시험지.pdf                       # 내용이 같은지 다시 검사
uv run examshield verify --profile a-remap-decoy --models local               # 이 프로파일의 효과 측정
```

`protect`는 복사본(`시험지.pdf`)과 작업 기록(`시험지.job.json`)을 쓴다. 배포하는 것은 PDF뿐이다. 작업 기록에는 미끼가 가리키는 답이 들어 있으므로 함께 배포하지 않는다. `--models local`은 텍스트 레이어 추출, Tesseract(설치돼 있으면), Ollama(떠 있으면)를 쓴다. 없는 것은 건너뛰고 리포트에 이유를 적는다.

`verify` 출력 예 (2026-11-20, 프로파일 `a-remap-decoy`, Tesseract 영어 데이터만 있고 Ollama는 없는 PC):

```
모델           경로           구분    글자 판독률  정답률  미끼 적중률  오류
text-layer     텍스트 레이어  대조군  100.0%       -       -            0
text-layer     텍스트 레이어  변환본  21.5%        -       -            0
tesseract-eng  이미지         대조군  40.4%        -       -            0
tesseract-eng  이미지         변환본  40.4%        -       -            0
건너뜀: ollama — Ollama(http://127.0.0.1:11434)에 연결하지 못했다. `ollama serve`가 떠 있는지 확인한다.
```

텍스트 레이어를 추출하면 원문의 21.5%만 맞는다. 쪽을 그림으로 읽는 경로(Tesseract)는 대조군과 변환본이 같다. 이 프로파일은 그림으로 읽는 AI를 막지 못한다는 뜻이다. Tesseract 수치 자체가 낮은 것은 문항이 한국어인데 한국어 데이터가 없어서다.

프로파일 목록과 검증 상태는 `uv run examshield profile list`로 본다. `a-` 프로파일 여섯 가지는 모두 `experimental`이다. 효과를 실제 AI로 확인하지 않았다.

## 사용법

명령별 설명은 **[USAGE.md](USAGE.md)**에 있다. 명령의 원래 설계는 [spec/06-commands.md](spec/06-commands.md)에 있다.

### 이 저장소 개발하기

```bash
uv sync --extra cloud    # 클라우드 SDK까지 설치해야 테스트가 전부 돈다
uv run pytest            # 테스트
uv run ruff check .      # 린트
uv run mypy              # 타입 검사
```

푸시 전 검사를 켜려면 저장소를 받은 뒤 한 번 실행한다.

```bash
git config core.hooksPath .githooks
```

그러면 `git push` 직전에 ruff, mypy, pytest가 돌고, 하나라도 실패하면 푸시가 막힌다. 서버에서 도는 CI는 쓰지 않는다. 각자 PC에서 도는 검사라 `git push --no-verify`로 건너뛸 수 있다.

## 알려진 한계

- 시나리오 A 기법 세 가지는 화면에 보이는 것을 바꾸지 않는다. 화면을 캡처하거나 쪽을 그림으로 읽는 AI에는 효과가 없다. 측정에서도 이미지 경로의 OCR 판독률은 변환 전후가 같았다.
- 글리프 매핑 변조는 PDF의 ToUnicode 표만 바꾼다. 글꼴 파일 안의 글자표를 직접 읽는 추출기는 원문을 복원할 수 있다. MuPDF와 poppler(`pdftotext`)로만 확인했다.
- 숨은 미끼는 정답을 모르고 무작위로 고른 번호를 가리킨다. 우연히 정답을 가리킬 수 있다(측정에서 12문항 중 2~5문항). `protect --answer-key`로 정답표를 주면 정답을 피하지만, 그러면 숨은 미끼 문구가 "정답이 아닌 번호" 하나를 알려 주게 된다. 정답표를 준 것처럼 만들어 Claude로 재 보니 텍스트 복사 경로의 정답률이 41.7%에서 0%로 떨어졌다(12문항 모두 미끼를 따름, 2026-11-21). Claude는 문제를 읽을 수 있으면 미끼를 거의 따르지 않았다(텍스트 경로 10문항 중 2문항, 그림과 PDF 경로 0문항). 글자를 섞어 문제를 못 읽게 했을 때만 미끼를 그대로 따랐다(7문항 중 7문항). 미끼 문구를 문제 위에 또렷하게 그려 넣고 그림으로 줘도 따르지 않았다(8문항 중 0문항, 정답률 100%). 그래서 눈에 보이는 미끼나 옅게 숨긴 미끼는 만들지 않았다. 한 모델, 한 가지 문구로 잰 결과다.
- `check`의 렌더링 비교는 MuPDF 한 가지로 한다. 다른 PDF 뷰어에서 다르게 보이는 경우는 잡지 못한다. 이미지화한 복사본은 그 해상도(기본 200dpi)에서 원본과 같다는 뜻이고, 더 확대하면 원본보다 흐리다.
- Word(.docx)와 한글(.hwp, .hwpx) 입력은 LibreOffice가 없는 PC에서 흉내 낸 변환기로만 테스트했다. LibreOffice가 같은 파일을 매번 같은 PDF로 바꾸는지, 변환 중 네트워크를 쓰지 않는지는 확인하지 못했다.
- 화면용 추적 워터마크(`a-watermark`, `a-full`)는 옅은 바탕 무늬다. 화면 캡처, 확대·축소, 일부만 자르기, JPEG 저장에는 남지만, 밝기를 올려 바탕을 하얗게 날리면 지워진다. 그 경우 `trace`는 아무도 지목하지 않는다. 여러 복사본을 겹쳐 평균 내는 공격, 글자를 새로 타이핑하는 유출도 막지 못한다.
- `trace`는 변환 전 원본, 매핑표, 시드 파일이 모두 있어야 한다. 종이를 찍은 사진은 점 무늬(`b-dots`) 복사본만 다룬다. 화면용 워터마크는 인쇄하면 사라진다.
- 워터마크 복원은 PDF를 MuPDF와 poppler로 그림으로 바꾼 것(해상도 72~220dpi, 일부 자르기, JPEG 품질 60 이상)으로 확인했다. 실제 화면 캡처 도구나 메신저가 다시 압축한 그림으로는 확인하지 못했다.
- 워터마크 무늬가 사람 눈에 얼마나 보이는지는 재지 않았다. 바탕을 최대 6/255(약 2%) 어둡게 한다. 모니터에 따라 옅은 격자가 보일 수 있다.
- 워터마크가 든 복사본은 `check`의 렌더링 비교 허용치가 2/255에서 8/255로 넓어진다. 대신 빈 바탕에서 덧씌운 무늬가 워터마크 격자 모양인지 확인한다. 옅은 글자를 덧씌운 것은 잡지만, 글자 위나 글자 가장자리에 숨긴 8/255 이하의 변조와 무늬 칸 단위로 그린 그림은 잡지 못한다.
- 클라우드 모델 연결 중 OpenAI와 Google은 실제 키로 호출해 본 적이 없다. Anthropic만 실제로 호출했다. 각 회사의 SDK가 보내는 요청을 같은 PC의 가짜 서버로 받아 확인했을 뿐이다. 가짜 서버의 응답 형식은 기억에 의존해 만들었으므로 실제 응답과 다를 수 있다.
- 기본 모델 이름(`gpt-6.2-sol`, `claude-opus-5-5`, `gemini-3.8-flash`) 중 OpenAI와 Google 것은 설치된 SDK에 적힌 이름에서 고른 추측이다. 그 회사의 대표 모델인지 확인하지 못했다. 환경변수로 바꿀 수 있다.
- `check`는 렌더링이 원본과 픽셀 단위로 같은 쪽을 OCR로 읽지 않는다. 그림이 같으면 OCR 결과도 같기 때문이다. 명세 6.2절의 "렌더링 결과를 OCR해 비교한다"를 그런 쪽에서는 생략하는 것이다. 12쪽짜리 약관 PDF의 `protect`가 약 20초에서 약 2초로 줄었다. 렌더링이 조금이라도 달라진 쪽은 그대로 OCR로 읽으므로, 그런 쪽이 많은 긴 문서는 여전히 느리다.
- `--copies`는 복사본 수에 비례해 느려진다. 12쪽짜리 내장 문항 PDF로 재면 복사본 하나에 `a-full`은 약 0.6초, `a-watermark`는 약 0.5초, `b-dots`는 약 0.7초가 든다. 복사본이 여덟 개 이상이면 여러 프로세스로 나눠 만든다(`--jobs`, 기본 최대 8). 수험번호 200개를 프로세스 8개로 만들어 보니 `a-full` 21초, `a-watermark` 15초, `b-dots` 21초였다(14코어 맥 한 대에서 한 번씩 잰 값). 프로세스를 더 늘려도 거의 줄지 않았다. 쪽수가 훨씬 많은 문서나 코어가 적은 PC에서는 재지 않았고, `trace`가 매핑표의 수험번호 수백 개를 비교하는 시간도 재지 않았다.
- 인쇄 시험 기능(`b-dots`, 사진에서 수험번호 복원, `calibrate`)은 촬영 시뮬레이션으로만 확인했다. 실제 프린터와 카메라로는 한 번도 해 보지 않았다. 점 하나는 한 변이 0.5pt(약 0.18mm)라서 프린터 해상도, 토너 번짐, 용지에 따라 찍히지 않거나 뭉개질 수 있다. 종이가 휘거나 접힌 사진, 쪽의 일부만 찍은 사진, 복사기로 다시 복사한 종이에서의 복원도 확인하지 못했다.
- 점 무늬는 AI 판독을 막지 못한다. Claude에 인쇄·촬영을 흉내 낸 그림을 줬을 때 판독률과 정답률이 무늬 없는 것과 똑같이 100%였다(2026-11-21, 한 모델, 12문항, 시뮬레이션). 그래서 `b-dots`는 유출 추적용으로만 다룬다. 점은 눈에 보이고(쪽 넓이의 약 0.35%), 사람의 가독성에 주는 영향은 재지 않았다. 저시력 수험생에게는 점 무늬가 없는 원본을 따로 발급해야 하는데, 그 복사본은 추적되지 않는다.
- 점 무늬 복사본의 `check`는 무늬 그림을 걷어 낸 쪽이 원본과 같은지, 무늬가 칸 가운데의 검은 점만으로 되어 있는지를 본다. 칸 가운데 점만으로 크게 그린 글자나 그림은 무늬와 구별하지 못한다.
- 명세가 시나리오 B 기법으로 든 문항별 의미 미끼는 만들지 않았다. 문항마다 사람이 설계해야 해서 자동으로 넣을 수 없다.
- `calibrate`가 내는 촬영 조건은 어림값이다. 시뮬레이션으로 찍은 그림에서도 잡음과 흐림은 실제보다 작게 읽힌다. 그래서 같은 방법으로 잰 실제 사진과 시뮬레이션의 값을 나란히 보여준다.
- 실제 AI로 잰 점수는 Claude 한 모델, 12문항, 프로파일 두 개가 전부다. 다른 회사 모델, 로컬 모델, 나머지 프로파일은 재지 않았다. Ollama 연결은 응답 형식을 흉내 낸 가짜 서버로만 테스트했다. 실제 Ollama에서 응답 형식이나 비전 기능 판별이 다르면 고쳐야 한다.
- 개발 PC의 Tesseract에 한국어 데이터가 없어서 한국어 OCR 기준선은 실제 값이 아니다.
- 촬영 시뮬레이션은 실제 인쇄·촬영과 비교해 보정한 적이 없다.
- 문항 세트는 쉬운 상식 문항이다(v1 12개, v2 36개). 정답률의 통계적 의미는 작고, 어려운 문항에서 AI가 어떻게 하는지는 알 수 없다. v2(쪽마다 문항 넷)로 Claude를 재 보니 텍스트 복사 경로의 정답률은 5.6~8.3%로 떨어졌다. 미끼를 따른 문항은 같은 조건에서도 36문항 중 4와 16으로 크게 달랐다. Claude는 쪽 단위로 미끼를 믿을지 정했고, 믿지 않은 쪽에서는 답을 내지 않았다. 숫자를 섞지 않는 프로파일(`a-remap-decoy-num`)은 한 번 잰 값이 36문항 중 17, 정답률 19.4%인데, 이 차이는 우연일 수 있다.
- `--models mock`의 `mock-reader`는 실제 AI가 아니다. 측정 파이프라인을 점검하는 용도다.
- 명세의 0단계(타당성 실험)는 하지 않았다. 실제 AI 모델과 API 키가 필요하다. `verify`로 돌릴 수 있다.
- 최신 멀티모달 AI에는 교란 폰트, 색 대비 왜곡, 방해선이 거의 효과가 없다는 연구가 있다. 어떤 기법도 통하지 않으면 방향을 "미끼 + 추적"으로 좁힌다 ([spec/12-risks.md](spec/12-risks.md)).
- 검증 기록은 `a-remap-decoy`와 `a-decoy` 두 개뿐이다. 시나리오 A 기법은 화면에 보이는 것을 바꾸지 않으므로 화면 캡처와 파일 올리기 경로는 어느 모델에서도 막지 못한다. 그래서 판정을 경로별로 나눴다. `a-remap-decoy`는 텍스트 복사 경로를 실제로 막으므로 "일부 경로만 막음"이고, `a-decoy`는 그 경로도 못 막아 `deprecated`로 표시했다. `deprecated`는 프로파일이 막겠다고 한 경로를 못 막았을 때만 쓴다. 명세 7절("기준 미달은 `deprecated`로 표시")보다 좁힌 기준이다.
- 드리프트 판정 기준(AI 모델마다 가장 잘 풀린 경로에서 변환본 정답률이 대조군의 절반 이하)과 30일은 명세에 숫자가 없어 임의로 정한 값이다. 문항이 12개라 한두 문항 차이로 판정이 바뀔 수 있다.
- 기준에 못 미친 프로파일을 `deprecated`로 바꾸는 일은 자동이 아니다. `protect`가 바꿔야 한다고 경고하고, 사람이 프로파일 YAML을 고친다.
- 한글 문서는 LibreOffice가 PDF로 바꾼 결과를 원본으로 삼는다. LibreOffice는 한글 문서의 글꼴, 표, 쪽 나눔을 그대로 옮기지 못할 수 있고, 버전에 따라 열지 못한다. `check`가 보장하는 것은 "바뀐 PDF와 복사본이 같다"까지다. 한글에서 본 모양과 같은지는 사람이 확인해야 한다. 확실한 방법은 한글에서 PDF로 내보낸 파일을 쓰는 것이다.
- 단일 실행 파일은 만든 맥(Apple Silicon)에서만 실행해 봤다. 다른 맥, 인텔 맥, 네트워크가 끊긴 PC에서는 확인하지 못했다. 서명과 공증을 하지 않아 다른 맥에서는 Gatekeeper가 막을 수 있다. 실행할 때마다 시스템 임시 폴더에 풀리고 시작에 약 4초가 걸린다. Windows용은 아직 없다.
- 실행 파일에는 Tesseract와 LibreOffice를 넣지 않았다. LibreOffice는 수백 MB이고, Tesseract는 Homebrew 라이브러리를 옮겨 묶는 과정이 깨지기 쉽다. 없으면 OCR 비교를 건너뛰고(그 사실을 적는다), Word와 한글 입력은 거부한다. 클라우드 SDK도 넣지 않아서 실행 파일로는 클라우드 모델 검증을 할 수 없다.
- 웹 화면은 복사본 만들기(파일 하나), 동일성 검사, 프로파일 보기만 한다. 수험번호별 복사본, 추적, 측정은 명령줄에서 한다. 크롬 한 가지로 화면이 뜨는 것만 확인했다. 올린 파일은 메모리에서 처리하고(파일 하나에 100MB까지) 문서는 한 번에 하나씩 처리한다.
- 안전 훅은 명령 문자열을 대조하는 안전망이다. 감싸거나 돌려 쓴 명령은 빠져나갈 수 있다.

## 요금

판매하는 것은 없다. 모든 기능의 코드가 이 저장소에 AGPL로 공개돼 있다. 프로파일 구독은 유료화하지 않기로 했다. 프로파일과 검증 기록은 저장소에 함께 둔다.

## 안전 훅

이 저장소에는 Claude Code 훅이 들어 있다(`.claude/settings.json`, `.claude/hooks/`). 이 저장소에서 Claude Code로 개발하는 동안 다음이 적용된다.

- **실행 전 차단** (`block-dangerous.sh`): 넓은 범위의 재귀 삭제, git 강제 푸시와 `reset --hard`, `clean -fd`, 비밀 파일이나 `docs/`·`secrets/` 스테이징, `curl | sh`, 패키지 공개 배포.
- **파일을 고칠 때마다 린트** (`lint-file.sh`): 고친 Python 파일에 ruff를 돌리고, 실패하면 내용을 에이전트에게 돌려보낸다.
- **끝내기 전에 테스트** (`run-tests.sh`): 테스트가 실패하면 작업을 끝내지 못한다.
- **읽기 거부 규칙**: `.env`, `.env.*`, `secrets/`.

훅은 실패 시 종료 코드 2로 끝난다. 그래야 실패 내용이 에이전트에게 전달된다. 훅 자체의 테스트는 `tests/test_hooks.py`에 있다.

## 데이터와 개인정보

- 시드 파일과 수험번호 매핑표는 `secrets/`에 둔다. `protect --copies`는 이 둘을 출력 폴더 안에 두는 것을 거부한다. 이 폴더와 `*.seed`, `.env`는 `.gitignore`로 제외돼 있다. 기관이 직접 보관한다.
- 출력 폴더(`out/`)와 로그도 커밋하지 않는다.
- 로그에는 파일 해시, 프로파일 이름, 시각만 남긴다. 문제 텍스트는 남기지 않는다.

## 로드맵

Phase 하나를 끝낼 때마다 결과를 확인받고 다음으로 넘어간다.

- [x] **Phase 0** — 프로젝트 골격: 명세 분할, 훅과 거부 규칙, 린트·타입 검사·푸시 전 검사, 문서 초안
- [x] **Phase 1** — `verify`: 문항 세트, 촬영 시뮬레이션, 기준선(텍스트 추출, Tesseract), 로컬 모델, 리포트. 완료 기준: 변환 없는 대조군 점수가 나온다
- [x] **Phase 2** — `protect` + `check`, 시나리오 A 프로파일(이미지화, 글리프 매핑 변조, 숨은 미끼). 완료 기준: 결정적 출력, 네트워크 0건 테스트 통과
- [x] **Phase 3** — `auth`, 클라우드 모델 검증, `--offline`. 완료 기준: 키 없이 실행하면 안내 후 종료, 호출 전 확인 절차 동작
- [x] **Phase 4** — 추적 워터마크, `--copies`, `trace`. 완료 기준: PDF와 화면 캡처 수준 이미지에서 수험번호 복원
- [x] **Phase 5** — 모델 드리프트 경고, `report`, `profile`, 문서 마무리. 완료 기준: 전체 테스트 통과
- [ ] **Phase 6** — 시나리오 B 인쇄용 프로파일, 실제 인쇄·촬영 보정, 촬영 사진에서 워터마크 복원. 코드는 구현했다. 완료 기준인 "시뮬레이션과 실촬영 결과 비교"는 실제로 인쇄해서 찍은 사진이 있어야 해서 남아 있다
- [ ] **Phase 7** — 폐쇄망용 단일 실행 파일, 라이선스, 웹 UI, 한글 입력. 코드는 구현했다(실행 파일은 macOS만). 완료 기준인 "폐쇄망 PC에서 설치·실행"은 그런 PC에서 해 봐야 해서 남아 있다. Windows용 실행 파일도 남아 있다. 프로파일 구독은 유료화하지 않기로 해서 만들지 않는다

명세의 단계별 계획([spec/11-plan.md](spec/11-plan.md))과의 대응: 명세 1~4단계가 Phase 1~4, 명세 5단계가 Phase 6, 명세 6단계가 Phase 7이다. `examshield trace`와 `examshield calibrate`는 명세의 명령 목록에 없다. 워터마크 복원과 실촬영 비교에 필요해서 추가한다.
